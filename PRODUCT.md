# Act Dock

## Platform
Electrobun 2.0.5 desktop app for macOS Apple Silicon, Windows x64, and Linux x64, with a React webview and independent Bun background runner. The Bun workspace also contains a TanStack Start landing page hosted on Cloudflare Workers.

## People and purpose
Developers and their local AI agents run GitHub Actions against local working files, inspect results, and iterate without pushing commits. Successful use means adding a project, finding a workflow, running it, and understanding its result from logs.

## Confirmed behavior
Saved local projects, workflow/job discovery, manual inputs, file-based environment/secrets, FIFO execution, cancellation, persisted history, CLI and MCP stdio. Agents may register any local folder and run without per-run prompts. Closing the desktop app preserves runs. On-demand startup is default; macOS login startup is optional.

## Constraints
Electrobun 2.0.5 and Hutch; shadcn/ui components; grayscale light/dark themes following the system by default, with green reserved for actively running pipelines. System fonts, accessible keyboard controls, and labeled status icons. No workflow editor, remote runners, hosted service, or account login. Optional GitHub and GitLab tokens allow branch pipeline lookups and pull/merge request review. Signing and notarization are outside v1.

## Bundled engine
act is shipped inside every installer (pinned version, checksum-verified at build time, MIT license included) and installed beside the runner. Resolution order: a custom act path from Settings, then the bundled engine, then the system act. Docker is the only external dependency.

## Project selection and history
Projects are selected using the native folder picker or the built-in folder browser, then explicitly confirmed; path typing is not required. Run history supports literal workflow/project/job/ID search, project/status/starter/date filters, counted pagination, and 10/25/50/100 rows per page. Filters and page selection survive opening a run and returning; removed projects remain filterable in retained history.

## Running feedback
Running workflows have a green animated outline, visible Running label, green status/count indicators, and a pinned current-step summary above output. Highlight the current step's log section while retaining readable neutral text. Parallel and nested steps follow act's lifecycle messages. Completed, queued, and cancelling runs use neutral status treatments. Reduced motion preserves the green outline without animation.

## Pull request review
While the app is open it polls each project's open pull/merge requests (60 s) and notifies when someone else's non-draft PR is opened or gets new commits; the first poll is a silent baseline. Opening a PR shows its description and per-file diffs. "Review with Claude" runs the user's local Claude Code CLI headlessly with every tool disabled, an empty working directory and no saved session; the PR text is treated as untrusted. The user can ask follow-up questions, then approve, send back (request changes) or comment from a dialog that always needs an explicit click and, for send back and comment, a message. Claude's draft message can prefill it. Posting uses the saved project/category token, so it needs write access to pull requests; a rejected token shows the provider's error. GitLab has no REST "request changes", so it is posted as a merge request note. Agents (MCP) can list, read, comment and request changes, but cannot approve.

## AI toolkit
The AI toolkit view scans the user's home folder (read-only) for local models (Ollama, Hugging Face, LM Studio, large loose model files) and for skills, agents and commands used by Claude, Codex, Gemini, Cursor, OpenCode and the shared `~/.agents` folder. It shows size, what each is for and how to use it, groups duplicates (skills linked to one shared folder count once; separate copies are identical or different), flags broken skill links with a suggested repair, and shows tool data (history, caches) read-only. Removal accepts only ids from the latest scan, always previews first, and moves items to the Trash (Ollama models move their manifest and only the blobs no other model uses). Models list the apps that use them ("Used by"), found in a second, slower pass from app bundles, app data and logs, config folders, project source and running processes; it is evidence from names found in files, not proof. Skills are grouped by category (frontend, backend, mobile, CI/CD, testing, security, git, data and AI, docs) with a Claude / Codex / Antigravity grid; a skill or a whole category can be installed into a tool as a link to the one real folder (default) or an independent copy, and removed per tool. The runner refuses to let an MCP caller confirm removals, repairs or installs (only the person in the app can); the MCP server does not currently register the toolkit's tools, so agents cannot reach it.

## Team and Jira
Members are plain name/email pairs with an optional GitHub or GitLab username, kept per project or per category (group). A project sees its own members plus its group's, each person once. They are managed in Project settings → Team & Jira, and from the gear beside a group in the sidebar. Jira is one connection per installation (Jira Cloud address, account email and API token; the token is stored encrypted on the machine and only sent to that site over HTTPS, redirects are refused). "Create Jira task" on the project page creates an issue in a chosen Jira project with an optional assignee chosen from the members. The assignee is resolved before anything is created, by email or, when Jira hides emails, by a name search whose result is linked to the member; a failed lookup never leaves an unassigned task behind. Nothing here is exposed to MCP agents.

## Status reports
Generate report (sidebar, Workspace, above AI toolkit) reads the local git history of every selected project for a date range (default: seven days before today through today, at most a year). It fetches each project's remotes first (30 s per repository; a failure is shown and the already-local history is used), then lists every branch's non-merge commits and changed files, up to 500 commits per repository and 200 files per commit. Authors are matched to Team members by email or by the login inside a GitHub/GitLab noreply address; other authors show as "not in Team", and members without commits are listed too. The person picks which people and repositories to include, then the user's local Claude Code CLI (every tool disabled, empty working directory, no saved session) fills an editable markdown template from commit messages, file paths and line counts only, never file contents. The template is stored per installation, starts as a built-in status report layout and can be reset. Without Claude, or when it fails, the plain activity list is returned with a note. Reports are not stored: they live on the page until the user leaves it.
This is activity, not delivery. Commits on every local and remote-tracking branch count, including unmerged and unreleased work, and the template's "achievements" and "milestones" are Claude's reading of those commits. Anything it cannot see (milestones, next steps) it marks "(to confirm)", and the person is expected to check the report before sending it. Not exposed to MCP agents.

The personal repository is MohammedIbrahim8887/act-dock. Public downloads live on GitHub Releases and are linked from https://act-dock.mohammedibrahim.dev. Packages include DMG, Windows installer, DEB, RPM, and AppImage. Native macOS and Linux startup can be checked locally; Windows GUI verification requires a Windows host. Main releases use a self-hosted runner on the owner's Mac, run checks through Act Dock, select a new patch version, publish installers and a checksummed manifest, and deploy the site without GitHub-hosted Actions minutes.

## Website
The landing page shows a coded, looping replica of the app running ci.yml instead of a static screenshot. It follows the desktop dark theme, pauses offscreen, has a visible pause control, and freezes on a mid-run frame for reduced motion. `/docs` covers install, first run, MCP setup per client (Claude Code, Codex, Cursor, Claude Desktop), tool reference, CLI, configuration, runner data, troubleshooting codes, and FAQ.
